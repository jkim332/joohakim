Real-Time Payment Analytics and Fraud Detection Pipeline

A streaming-data demo that generates payment events, applies fraud rules, and makes transaction activity visible in a live dashboard.

결제 이벤트를 생성해서 사기 탐지 규칙을 적용하며, 실시간 대시보드에서 거래 현황을 확인할 수 있는 스트리밍 데이터 데모 프로젝트.

1. Why does it matter? / 왜 중요한가?

Digital payments move quickly and generate large volumes of transactions, making manual fraud detection difficult to scale. Suspicious activity can lead to financial losses, costly investigations, and disrupted experiences for clients. This project explores how stream processing can detect unusual payment activity in real-time and help analysts understand why transactions are flagged. Using fake payment data, it demonstrates an end-to-end fraud detection workflow.

디지털 결제는 빠르게 움직이면서 대량의 거래가 발생되기 때문에 수동으로 사기 거래를 탐지하는 데 한계가 있습니다. 의심스러운 거래는 금전적 손실과 조사 비용을 초래할 수 있으며, 정상적인 고객의 결제가 차단되는 문제로 이어질 수도 있습니다.

3. The solution / 해결책

Stage 1 — Generate events and stream them through Kafka

The Python producer emits realistic-shaped JSON payment events at a configurable rate (100 per second by default), including occasional scenarios designed to trigger the fraud rules. Kafka provides a durable buffer between production and processing, so the consumer can work through events in batches rather than coupling generation directly to database writes. The payments topic has three partitions: this gives the demo room for parallel consumption while keeping the setup manageable. Events use user_id as their key, so one user's events are routed to the same partition and retain their partition order—important for rules that depend on recent activity.

Python 프로듀서는 초당 기본 100건의 JSON 결제 이벤트를 생성하며, 사기 탐지 규칙이 작동하도록 설계된 시나리오도 간헐적으로 포함합니다. Kafka는 이벤트 생성과 처리를 분리하는 내구성 있는 버퍼 역할을 하므로, 컨슈머가 데이터베이스 쓰기와 직접 결합되지 않고 이벤트를 배치 단위로 처리할 수 있습니다. payments 토픽은 데모에서 병렬 처리를 가능하게 하면서도 구성을 단순하게 유지하도록 3개 파티션으로 설정했습니다. 이벤트 키로 user_id를 사용해 한 사용자의 이벤트를 같은 파티션으로 보내고 파티션 내 순서를 유지합니다. 이는 최근 활동 내역을 기준으로 판단하는 규칙에 중요합니다.

Stage 2 — Validate events and calculate risk

The Python batch consumer validates incoming records, maintains bounded recent activity per user, and applies configurable rules for large payments, rapid transactions, repeated declines, and country changes. Triggered rule weights are summed and capped at 100. Any matched rule marks the event as suspicious and records the reasons, making each score straightforward to inspect. The consumer manually commits Kafka offsets only after a database batch succeeds, and restores its detector state if that batch fails.

Python 배치 컨슈머는 입력 레코드를 검증하고 사용자별 최근 활동을 제한된 상태로 유지하며, 고액 결제·짧은 시간 내 반복 거래·반복 거절·국가 변경 규칙을 적용합니다. 작동한 규칙의 가중치를 합산해 최대 100점으로 제한합니다. 하나 이상의 규칙이 일치하면 의심 거래로 표시하고 사유를 함께 기록해 점수를 쉽게 확인할 수 있습니다. 컨슈머는 ClickHouse 배치 저장이 성공한 뒤에만 Kafka 오프셋을 수동 커밋하며, 저장에 실패하면 탐지기 상태를 복원합니다.

Stage 3 — Batch writes into ClickHouse for analytics

ClickHouse was chosen as a column-oriented analytical database: its strengths fit dashboard queries that aggregate large numbers of transactions by time, merchant, status, or risk. The consumer inserts up to 500 events per batch, or polls for up to 1,000 ms, balancing efficient bulk writes with bounded wait time before a batch is sent. The table uses ReplacingMergeTree(ingested_at) so newer versions of a transaction can replace earlier ones during background merges. Monthly partitions on event_time help time-range queries skip irrelevant months, while ordering by (event_date, transaction_id) supports date-scoped transaction lookups. Event timestamps are stored in UTC for consistent time-based analysis.

ClickHouse는 열 지향 분석 데이터베이스로, 시간·가맹점·상태·위험도별로 많은 거래를 집계하는 대시보드 쿼리에 적합해 선택했습니다. 컨슈머는 한 배치에 최대 500건을 저장하거나 최대 1,000ms 동안 폴링한 뒤 전송합니다. 이를 통해 대량 쓰기의 효율을 높이면서 배치 전송까지의 대기 시간도 제한합니다. 테이블은 ReplacingMergeTree(ingested_at)를 사용해 백그라운드 병합 시 같은 거래의 이전 버전 대신 더 최신 버전을 남길 수 있도록 했습니다. event_time 기준 월별 파티셔닝은 기간 조회 시 불필요한 월을 건너뛰는 데 도움이 되고, (event_date, transaction_id) 정렬 키는 날짜 범위 거래 조회를 지원합니다. 이벤트 시간은 일관된 시간 분석을 위해 UTC로 저장합니다.

Stage 4 — Explore the results in Grafana

Grafana queries the enriched ClickHouse records and presents transaction volume and value, approval and suspicious rates, fraud reasons, merchant performance, highest-risk users, and suspicious transaction details. Docker Compose brings the services together so the full synthetic-data workflow can be run and explored locally.

Grafana는 사기 탐지 정보가 추가된 ClickHouse 데이터를 조회해 거래량과 결제 금액, 승인율과 의심 거래 비율, 탐지 사유, 가맹점별 성과, 위험도가 높은 사용자, 의심 거래 상세 정보를 보여줍니다. Docker Compose로 서비스를 함께 실행할 수 있어 합성 데이터를 이용한 전체 흐름을 로컬에서 재현하고 살펴볼 수 있습니다.

The Result / 결과

The result is a working, locally runnable reference pipeline that connects event generation, Kafka streaming, rule-based enrichment, analytical storage, and dashboarding. The included Grafana dashboard covers transaction count and value, approval and suspicious rates, payment volume over time, fraud reasons, transaction status, merchant performance, highest-risk users, and suspicious transaction details.

The rules are covered by focused tests for thresholds, time windows, score capping, and detector-state restoration after a failed batch. Together, the implementation and dashboard demonstrate how streaming infrastructure can turn raw payment events into inspectable alerts and analytics.

Scope of the result: the producer creates synthetic data and its configured rate is 100 events per second. That is a demo setting, not a benchmark result. The project does not report fraud-detection accuracy, false-positive rates, latency, or production-scale performance.

Tradeoffs and other possible solutions

  • Rules are simple and explainable, but limited. Fixed thresholds can miss new fraud patterns and may flag legitimate unusual behavior. A supervised model trained on labeled historical transactions could capture more complex patterns, but would require representative labels, ongoing evaluation, drift monitoring, and a human review strategy.
  • The input is synthetic. Generated events are useful for repeatable testing, but cannot establish real-world accuracy or reflect all customer behaviors. A privacy-controlled, representative dataset and a carefully designed offline/online evaluation would be needed to assess effectiveness.
  • Per-user state is held in the consumer process. This keeps the demo straightforward, but state recovery and consistent scoring across consumer restarts or rebalances are important production concerns. A shared state store or Kafka Streams/Flink with managed state and checkpointing could provide a more robust foundation.
  • The stack favors a compact, self-managed demo. Operating Kafka, ClickHouse, and Grafana brings deployment and monitoring overhead. For a smaller workload, a managed queue plus a conventional database may be simpler; at larger scale, a managed streaming platform or Flink-based pipeline may offer stronger operational tooling.
  • Batching trades write efficiency against freshness. Larger batches can improve database insert efficiency but may delay visibility. Production tuning should use measured throughput and end-to-end latency, plus explicit retry, deduplication, alerting, and data-retention policies.
