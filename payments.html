Real-Time Payment Analytics and Fraud Detection Pipeline

A streaming-data demo that generates payment events, applies fraud rules, and makes transaction activity visible in a live dashboard.

  • Python
  • Kafka
  • ClickHouse
  • Grafana
View project on GitHub ↗

1. Why does it matter?

Digital payments move quickly and generate large volumes of transactions, making manual fraud detection difficult to scale. Suspicious activity can lead to financial losses, costly investigations, and disrupted experiences for clients.

This project explores how stream processing can detect unusual payment activity in real-time and help analysts understand why transactions are flagged. Using fake payment data, it demonstrates an end-to-end fraud detection workflow.

3. The solution

Stage 1 — Generate events and stream them through Kafka

The Python producer creates 100 events/sec in JSON format, including occasional scenarios designed to trigger the fraud rules.
Kafka provides a buffer between production and processing, so the consumer can work through events in batches. The payments topic is set up for 3 partitions. Events use user_id as their key, where the user's activity is detected quickly by sending their events to the same partition.

Stage 2 — Validate events and calculate risk

The Python batch consumer validates incoming records, maintains recent activity per user, and applies fraud rules (see below for rules).
Triggered rule weights are summed and capped at 100. Any matched rule marks the event as suspicious and records the reasons, making each score straightforward to inspect.
The consumer manually commits Kafka offsets only after a database batch succeeds, and restores its detector state if that batch fails.

Stage 3 — Batch writes into ClickHouse

ClickHouse was chosen as a column-oriented analytical database, for quick analytical queries.
Consumer inserts up to 500 events per batch, or polls for up to 1,000 ms, balancing efficient bulk writes with bounded wait time before a batch is sent. The table uses ReplacingMergeTree so newer versions of a transaction can replace earlier ones during background merges.
Monthly partitions on event_time help time-range queries skip irrelevant months, while ordering by (event_date, transaction_id) supports date-scoped transaction lookups.

Stage 4 — Explore the results in Grafana

Grafana queries the ClickHouse records and presents transaction volume and value, approval and suspicious rates, fraud reasons, merchant performance, highest-risk users, and suspicious transaction details.

4. The Result

The result is a working, locally runnable reference pipeline that connects event generation, Kafka streaming, analytical storage, and dashboarding. It was designed to be simple, but realistic enough to demonstrate the end-to-end flow of a real-time payment fraud detection system.

Tradeoffs and other possible solutions

  • State recovery - This keeps the demo straightforward, but state recovery and consistent scoring across consumer restarts or rebalances are important production concerns. A shared state store or Kafka Streams/Flink with managed state and checkpointing could provide a more robust foundation.
  • Workload sizes - Operating Kafka, ClickHouse, and Grafana brings deployment and monitoring overhead. For a smaller workload, a managed queue plus a conventional database may be simpler; at larger scale, a managed streaming platform or Flink-based pipeline may offer stronger operational tooling.
  • Batch considerations - Larger batches can improve database insert efficiency but may delay visibility. Production tuning should use measured throughput and end-to-end latency, plus explicit retry, deduplication, alerting, and data-retention policies.
