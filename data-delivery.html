Multi-Source Data Orchestration and Client Data Delivery Automation

An automatedSLA-driven pipeline design for extracting, transforming and delivering big data to client-specific destinations across multiple platforms.

  • Apache Airflow
  • dbt
  • Databricks
  • AWS S3
  • Azure Blob Storage
  • Google Cloud Storage
  • Snowflake
  • Kubernetes

1. Why does it matter?

The delivery window is fixed: clients must have their data by Monday at 9:00 AM EST. Analysts need the data to perform automated data quality checks before this timeframe. Each run moves approximately 500 GB through transformations and out to 50+ AWS S3 buckets, 10+ Azure blobs, 10+ GCS accounts, and 50+ Snowflake accounts.

Coordinating many client-specific deliveries is a scheduling problem as much as a data-processing problem. Slow transformations, insufficient worker capacity, service limits, or uneven destination workloads can consume the time reserved for delivery. Finishing a transformation is not the same as making its result available: each destination transfer must complete and be verified before the SLA.

The workflow therefore needs observable per-client status, isolated failures, safe retries, and enough schedule buffer to recover from variable transfer speeds or downstream delays without obscuring which clients are still waiting.

3. The solution

Triggers: To start the workflow, we would need to ensure that there are triggers. We can utilize event-driven triggers to detect for checksum or SUCCESS files in the new raw data folder. This can then trigger Airflow DAG through API.

ETL: Trigger DBT/Databricks through API. DBT transforms and loads data into Snowflake for analysts. Databricks reads raw data imported from Snowflake, partitions it, and writes the delivery data back to AWS S3. Have Airflow task poll for completion of the jobs so it can run downstream tasks.

Airflow orchestration: The ingested metadata stores client data, which is read in Airflow to generate dynamic tasks. Retain a TaskGroup for each delivery type, then set to run the longest running ones first ([Azure, GCS, S3] -> Snowflake).

Concurrency: Use KubernetesPodOperator instead of PythonOperator to run tasks in parallel and prevent from using Airflow resources. Set concurrency limits which should account for task durations, worker capacity, network and S3 throughput.

4. The result

A sample Airflow graph. Blue tasks are TaskGroups.

The design coordinates S3/Azure/GCS/Snowflake destinations by Monday 9:00 AM EST delivery deadline for a workload of approximately 500 GB per client.

Meeting the SLA still depends on realistic runtime estimates, capacity planning, monitoring, safe retries, and schedule buffer for variable transfers and downstream delays. Execution order alone cannot guarantee the deadline; delivery completion must be verified at each destination.

5. Trade-offs

  • Concurrency vs. resource contention. More client tasks in parallel can reduce elapsed time, but increase worker, network, API, S3, and Snowflake pressure. Limits should be raised only where measured capacity and service quotas support it.
  • TaskGroup organization. Groups improve graph readability and operational visibility, but do not throttle tasks or guarantee an execution sequence. Dependencies, pools, and concurrency settings provide those controls.
  • Retries vs. duplicate effects. Retrying a failed delivery improves recoverability, but a timeout may happen after data reached the client. Idempotent writes, run identifiers, or destination-side verification help avoid duplicate or inconsistent results.

Potential optimization: partition-based Dynamic Task Mapping

For larger datasets, Airflow Dynamic Task Mapping is a potential optimization to evaluate and benchmark—not an implemented or proven improvement. A discovery task could inspect the total number of S3 partitions then have each task a manageable group of partitions rather than one task for all partitions.

Task mapping would distribute large runs across workers and easier to isolate and retry per batch, instead of retrying the entire run. However, the mapping needs bounds. Mapping every partition individually can overload the scheduler or metadata database; and excessive parallelism can overload the network bandwidth, requests, worker resources. The number of simultaneously running mapped tasks should be carefully adjusted with Airflow concurrency controls and pools.
