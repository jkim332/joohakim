Multi-Source Data Orchestration and Client Data Delivery Automation

여러 플랫폼에서 대용량 데이터를 추출·변환하고 고객에게 전달하기 위한 파이프라인 설계.

  • Apache Airflow
  • dbt
  • Databricks
  • AWS S3
  • Azure Blob Storage
  • Google Cloud Storage
  • Snowflake
  • Kubernetes

1. 왜 중요한가?

고객사는 미국 동부시간(EST) 기준 월요일 오전 9시까지 데이터를 받아야 하고, 그 전에 분석가들이 자동화된 데이터 품질 검증까지 마칠 수 있어야 합니다.

한 번 실행할 때마다 약 500GB 규모의 데이터가 변환되며, 이후 이 데이터는 50개가 넘는 AWS S3 버킷, 10개 이상의 Azure Blob Storage, 10개 이상의 GCS 계정, 그리고 50개 이상의 Snowflake 계정으로 전달됩니다.

여기서는 단순히 데이터를 가공하는 문제를 넘어, 정교한 스케줄링이 필요한 운영 문제이기도 합니다. 변환 속도가 느리거나, 워커 용량이 부족하거나, 서비스별 제한이 걸리거나, 목적지별 작업량이 고르지 않으면 정작 데이터 전달에 써야 할 시간이 줄어들 수 있습니다. 게다가 변환이 끝났다고 해서 일이 끝나는 것도 아닙니다. 각 목적지로 데이터가 실제로 전송되고, SLA 시간 안에 검증까지 완료되어야 비로소 전체 작업이 끝난 것입니다.

그래서 이 플로우에서는 고객사별 진행 상태를 한눈에 파악할 수 있는 기능, 문제를 분리할 수 있는 구조, 안전하게 재시도할 수 있는 메커니즘, 그리고 전송 속도 저하나 다운스트림 지연이 발생해도 흡수할 수 있는 충분한 일정 여유가 필요합니다. 동시에, 어느 고객사가 아직 데이터를 기다리고 있는지도 명확하게 확인할 수 있어야 합니다.

3. 해결 방안

트리거: 파이프라인을 시작하려면 트리거가 필요합니다. 이벤트 기반 트리거를 사용하면 새 데이터 폴더에 checksum 파일이나 SUCCESS 파일이 생성되었는지 감지할 수 있습니다. 새 데이터가 확인되면 API를 통해 Airflow DAG를 실행합니다.

ETL: API를 통해 dbt와 Databricks 작업을 실행합니다. dbt는 데이터를 변환해 분석용 데이터를 Snowflake에 적재하고, Databricks는 Snowflake에서 가져온 데이터를 읽어 파티셔닝한 뒤, 전달용 데이터를 AWS S3에 다시 저장합니다. 이후 Airflow 태스크가 작업 완료 여부를 폴링하고, 완료가 확인되면 다음 태스크를 실행합니다.

Airflow 오케스트레이션: 수집된 메타데이터에는 고객 데이터 정보가 포함되며, Airflow는 이걸 사용해 태스크를 알아서 생성합니다. 전달 유형별로 TaskGroup을 구성하고, 실행 시간이 가장 오래 걸리는 작업이 먼저 시작되도록 [Azure, GCS, S3] → Snowflake 순서로 운영합니다.

동시성: Airflow 리소스 사용을 줄이고 태스크를 병렬로 실행하기 위해 PythonOperator 대신 KubernetesPodOperator를 사용합니다. 또한 태스크 실행 시간, 워커 용량, 네트워크 대역폭, S3 처리량을 고려해 한도를 설정합니다.

4. 결과

Airflow 그래프 예시입니다. 파란색 태스크는 TaskGroup입니다.

이 설계는 고객당 약 500GB의 데이터를 월요일 오전 9시(미국 동부 표준시)까지 S3, Azure, GCS 및 Snowflake 목적지로 전달하는 작업을 그려냅니다.

SLA 준수에는 현실적인 실행 시간 추정, 용량 계획, 모니터링, 안전한 재시도, 그리고 전송 지연에 대비한 조율이 필요합니다. 실행 순서만으로 전달 시간을 보장할 수는 없으며, 각 목적지에서 전달 완료 여부를 확인해야 합니다.

5. 고려 사항

  • 동시성과 리소스 경합. 고객별 태스크를 더 많이 병렬로 실행하면 전체 처리 시간은 줄어들 수 있지만, 그만큼 작업자, 네트워크, API, S3, Snowflake에 걸리는 부하도 함께 커집니다. 따라서 한도 상향은 실제 측정된 처리 용량과 서비스 할당량이 충분히 뒷받침될 때만 신중하게 적용해야 합니다.
  • TaskGroup 구성. TaskGroup은 관련 태스크를 논리적으로 묶어 운영과 관리 편의성을 높여주지만, 태스크 수를 제한하거나 실행 순서를 보장하는 기능까지 제공하지는 않습니다.
  • 재시도와 중복 처리. 실패한 전달을 재시도하면 복구는 쉬워지지만, 이미 고객에게 데이터가 정상적으로 도착한 뒤에 타임아웃이 발생하는 경우도 있을 수 있습니다. 이런 상황에 대비하려면 idempotent 저장 방식, 실행 식별자, 또는 고객 측 검증 절차를 통해 중복 전송이나 불일치 결과를 방지하는 것이 좋습니다.

최적화 방안: 파티션 별 Dynamic Task Mapping

대용량 데이터 전달에서는 Airflow Dynamic Task Mapping을 최적화 방안으로 검토해볼 수 있습니다. 예를 들어 추가 태스크가 S3 파티션 수를 확인한 뒤, 전체 파티션을 하나의 태스크에서 처리하는 대신 여러 파티션 묶음을 각 태스크에 할당해 작업을 분산할 수 있습니다.

태스크 매핑을 활용하면 대규모 실행을 여러 워커에 나눠 처리할 수 있고, 전체 실행을 다시 시도하는 대신 실패한 배치만 분리해 재시도할 수 있습니다. 다만 매핑 범위는 적절히 제한해야 합니다. 파티션마다 태스크를 생성하면 스케줄러나 메타데이터 데이터베이스에 부담을 줄 수 있고, 지나친 병렬 실행은 네트워크 대역폭, 요청 한도, 워커 리소스를 빠르게 소모할 수 있습니다. 따라서 동시에 실행할 매핑 태스크 수는 Airflow의 동시성 제어와 풀(pool)을 활용해 신중하게 조정하는 것이 좋습니다.
